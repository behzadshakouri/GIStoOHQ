# Known-rainfall and receiving-area acceptance

The19November2026 check uses the real GIStoOHQ rainfall writer and real OHQ
console, without observations or fitting. One shared Precipitation source serves
two catchments of1000and2500m². Its native file specifies0.01m interval-total
depth over one day. The0.1day test therefore supplies0.001m rainfall:3.5m³
over the combined area. Receiver rain rates must be10and25m³/day, respectively.
The areas are swapped in a third run to detect accidental shared-source caching
or a coefficient bound to the first receiver.

The tests include fixed discharges into a collector and an independent analytic
storage solution. A second run uses60%runoff and first-order storage loss at
0.2/day. The ledger is rainfall minus catchment storage change, collector
discharge, first-order loss and non-runoff rainfall loss. Conservative and
swapped-area residuals are1.14e-15m³. The loss-case residual is-4.21e-5m³ on
3.5m³ input, inside the prospectively set0.001m³ check tolerance. Solver output
must also be finite and agree with the analytic solution; a plausible ledger
alone is insufficient.

```
python3 scripts/verify_ohq_rainfall_ledger.py VERIFIED_CONSOLE \
  OHQ_RESOURCES NEW_OUTPUT_DIRECTORY
```

Source/executable/resource/writer/script/model/forcing/output hashes accompany
the results. Outputs are new files; previous evidence is never overwritten.

## Rain-area warning: fixed without changing physics

The original warning was generated by `Object::CalculateInitialValues`, which
evaluated the source's `coefficient=area` expression on Rain itself. That
coefficient belongs to the RECEIVER; `Source::GetValue(receiver)` already uses
the correct context. Generic source initialization now skips this coefficient,
matching the existing exclusion in `System::CalculateAllExpressions`.
OpenHydroQual commit28dcc2b contains only that fix and a regression description;
the pre-existing modified console main was left untouched.

All3synthetic output tables and all4generated-formulation short startup tables
are byte-identical before/after the fix. The warning disappears, and invalid
channel length/soil moisture still reject. This was a context-warning fix, not
an improvement to the already-correct rainfall volumes or a fitted correction.

## Plugin execution acceptance

`scripts/verify_qgis_plugin_lifecycle.py NEW_OUTPUT --saved-gis SAVED_OUTPUTS`
can now copy the4required saved GIS inputs into an isolated project, click the
real Build OHQ, Build HEC-HMS and Validate HEC-HMS buttons, and wait for their
actual QProcess commands. All3commands passed;4OHQ formulations and a native HMS
bundle were produced. Both preserved and copied GIS input hashes stayed
unchanged. No installed plugin/profile or source project was changed.

This uses actual offscreen QGIS/Qt widgets with a minimal interface adapter,
not a human-operated desktop/map-canvas session. The replay uses the preserved
historical GIStoOHQ GIS, not a newly generated full29.2km² project. HEC-HMS
structural validation is not an HMS simulation. The simple synthetic ledger
does not establish full-HRU/field-event balance or predictive skill. Fresh
DEM/full-run acceptance and a complete generated-model event ledger remain
separate work; no research-training budget is granted by these checks.
